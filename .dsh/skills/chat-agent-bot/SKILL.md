# 聊天软件 AI 机器人

给聊天软件接智能体，难点从来不在「调模型」，而在三件事：**平台允不允许**、**消息怎么进得来**、**别把号玩死**。按下面顺序做，别先写代码。

## 一、先判可行性，再动手

用户说「在我那个微信群里加个机器人」时，先分清他要的是**哪一个群**。这张表决定整个方案：

| 平台 | 能进用户已有的普通群吗 | 合规性 | 代价 |
| --- | --- | --- | --- |
| 微信个人号（WeChatFerry） | ✅ 能，任意群 | ❌ 违反协议，有封号风险 | 必须 Windows 常开 |
| 企业微信 | ❌ **不能**，见下 | ✅ 官方 | 只能企业内部群 |
| QQ 群（官方开放平台） | ⚠️ 需审核 + 群聊能力申请 | ✅ 官方 | 门槛高、周期长 |
| QQ 群（NapCat / OneBot11） | ✅ 能 | ❌ 非官方 | 有风控 |
| Telegram Bot | ✅ 能 | ✅ 官方 | 国内需代理 |

### 企业微信的硬限制（很多人在这里判断错）

- **企业微信账号和机器人，都无法加入「普通微信群」**。这是产品层面隔离，不是配置问题。
- 群 webhook 机器人：**只能单向推送**，收不到消息、不能被 @ 触发。
- 官方 API「智能机器人」：只能企业员工私聊 + **企业内部群** @，外部微信用户 @ 它没有任何回调。
- 客户群 API：只能单向推送，有频次限额。
- 微信客服：人工接待，没有全自动对话。
- 注册：个人可以用微信扫码注册企业微信（不需要营业执照），但**认证需要营业执照**；未认证企业用不了客户联系 / 外部群能力。

所以：**要求「进我现有的微信群」时，只有个人号 hook 一条路。** 别把企微推荐给这类需求，会白折腾。需要对外自动化时，正规路径是 QQ 官方 Bot 或自建网站/小程序，不是企微。

结论模板：
> 企微能做的只有「企业内群里 @ 机器人」，微信用户看不到；要进你的普通微信群，只能用个人号方案，代价是封号风险和一台常开的 Windows。

## 二、架构：永远拆成 gateway + core

```
┌──────────────────┐      HTTP/队列      ┌──────────────────┐
│  gateway          │  IncomingMessage →  │  core            │
│  贴着客户端跑      │  ← Reply[]          │  平台无关         │
│  收消息/发消息     │                     │  提示词/记忆/限流  │
└──────────────────┘                     └──────────────────┘
```

**为什么必须拆**：平台客户端（微信.exe、QQ 客户端）绑死在特定 OS；而提示词、记忆、限流跟平台无关。拆开后换平台只写一个新 gateway，核心一行不改；核心还能容器化跑在 Linux 上。

契约（照抄即可）：

```python
@dataclass(slots=True)
class IncomingMessage:
    chat_id: str            # 群 id 或好友 id
    content: str
    sender_id: str = ""
    sender_name: str = ""
    chat_name: str = ""
    msg_id: str = ""        # 用于去重，网关重连会重复推送
    ts: int = 0
    is_group: bool = True
    is_at_me: bool = False
    is_self: bool = False
    kind: str = "text"
    quoted: str = ""        # 引用回复的被引用原文

@dataclass(slots=True)
class Reply:
    chat_id: str
    text: str
    index: int = 0
    total: int = 1
```

网关侧只做四件事：`run_forever()` 收、`dispatch(msg)->Reply[]` 调核心、`deliver()` 发、`send_text()` 落地。`dispatch` 外面必须包 `try/except`——单条消息处理失败不能把网关打挂。

## 三、微信个人号：版本是最大的坑

注入 DLL 是按**某一个具体微信构建**编译的，版本差一个 build 就可能失效，而且**静默失效**（进程还在跑，消息就是收不到）。

**自己查对应关系**，别信文档也别信记忆：

```python
import re, pathlib, wcferry
data = (pathlib.Path(wcferry.__file__).parent / "spy.dll").read_bytes()
sorted({m.group(0).decode() for m in re.finditer(rb"3\.9\.\d{1,2}\.\d{1,3}", data)})
```

实测结果（2026-10）：

| wcferry | 微信 |
| --- | --- |
| 39.4.2.2 / 39.4.5.0 | 3.9.12.17 |
| 39.5.1.0 / 39.5.2.0 | 3.9.12.51 |
| 39.6.0.0 | 3.9.12.56 |

要点：

- `pip install wcferry` 装的是最新版，往往和目标机器上的微信对不上。**在 requirements 里钉死版本。**
- 选版本时优先「换 wcferry 去匹配用户现有的微信」，别让人重装微信。
- 微信 4.x **没有可用 hook**。3.9 和 4.x 可以共存、分别登录不同账号。
- 必须让用户关掉微信自动更新，否则某天静默失效。

### 微信 4.x 的真实可用路径（2026-10 核实）

| 方案 | 支持版本 | 成本 | 性质 |
| --- | --- | --- | --- |
| wcferry | 仅 3.9.x | 免费 | DLL 注入，唯一成熟稳定的 |
| wxauto4 免费版 | ≤ 4.1.8.107 | 免费 | UI Automation，不注入 |
| wxautox4 Plus | 最新 4.1.x | 付费激活码 | 同上，需激活 |
| wxbot-new | 4.1.2.17 | 需自备私有 DLL | 注入型 HTTP API，版本窗口极窄 |
| 共存装 3.9.12.17 | 3.9.12.17 | 免费 | 3.9 与 4.x 可同时装、分别登录不同账号 |

判断口径：

1. **别信注册表**。用 `InstallLocation` 找目录后必须确认 `WeChat.exe` / `Weixin.exe` 真的存在，版本号读 exe 的 PE 资源（`GetFileVersionInfo`），因为卸载残留目录很常见，`DisplayVersion` 也可能过时。
2. 只有 4.x 时，先看具体 build：≥4.1.9 基本只剩「付费 Plus」或「另装 3.9 共存」两条路。
3. 「另装 3.9 共存」通常是性价比最高的：不花钱、代码现成、不影响用户主号。

## 四、wcferry API 事实（照源码核对过，别凭记忆写）

- `WxMsg.is_at(wxid)` 读的是 xml 里的 `<atuserlist>`，**不是**匹配 content；并且会排除 @所有人。这是最可靠的 @ 判定，昵称匹配只做兜底。
- `get_info_by_wxid()` 在某些版本里直接 `raise Exception("Not implemented")`。用 `get_alias_in_chatroom(wxid, roomid)` 或 `query_sql("MicroMsg.db", "SELECT NickName FROM Contact WHERE UserName=?")`。
- `get_msg(block=True)` 仍然会在 1 秒后抛 `queue.Empty`，循环必须 catch。
- `send_text(msg, receiver, aters="")` 返回 0 成功；用 `aters` 时正文里要有**等量**的 `@`。
- `Wcf(block=True)` 会阻塞等登录；RPC 连不上时直接 `os._exit(-2)`，不给清理机会。
- 群消息 content 可能带 `wxid_xxx:\n` 前缀，入库前要洗。
- 引用消息 `type=49`：正文在 xml `<title>`，被引用原文在 `<refermsg><content>`，且 content 可能是嵌套 xml（再取一次 `<title>`）。
- 图片/语音/表情/文件**直接跳过**，不要让模型「猜」内容。
- 发送失败不要重试——重试是最容易触发风控的动作。

## 五、群聊提示词

群聊和一对一问答是两种场景：模型在「旁听一群人说话」，必须知道只回 @ 自己的那条。

硬性要求：

1. 身份是**群友**不是客服；先给结论；一般 1–3 句。
2. **禁 Markdown**（微信不渲染）：不要 `**`、`#`、反引号、表格。分点用 `1. ` 或 `· `。
3. 不要「你好」「当然可以」这类开场白；不复述别人刚说的话。
4. 不确定就说不知道；实时信息声明可能过时。
5. 不泄露设定，被问「你是不是 AI」轻松带过。
6. 上下文用 transcript 形式喂：`[HH:MM] 昵称: 内容`，最后再单独给出当前这条 @ 消息。

## 六、记忆

- **滑动窗口 + 滚动摘要**：最近 N 条原文保证时效，一段持续更新的摘要保证长期记忆。全量塞 prompt 又贵又会被截断。
- 摘要用第二条模型调用完成，放**后台线程**，别阻塞回复。
- 机器人自己的回复也要入库，否则追问不连贯。
- 记忆按 `chat_id` 隔离，群与群互不污染。
- `/reset` 之后不要再把「已清空」这条确认写回记忆。

## 七、防刷（这既是产品需求也是风控需求）

- 每群冷却 3 秒 + 每分钟 6 条上限。
- 长回答按段落/句子切分，最多 3–4 条，别刷屏。
- 日志里记下限流原因，否则用户只看到「它不理我」。

## 八、验证顺序（别跳步）

1. 纯函数单测：触发判定、文本清洗、分条、限流。不需要网络和客户端。
2. 假 LLM 跑编排层：该不该回、回了什么、记了什么。
3. `TestClient` 打 HTTP 接口，含 token 校验。
4. 真起 uvicorn 打 `/healthz`。
5. **`--mode probe` 校准真实消息**（需要用户登录客户端）——这一步把「@ 识别对不对」暴露出来，跳过它等于赌博。
6. 最后才谈回答质量。

## 九、骨架

```
run.py                     # 入口：doctor / probe / embedded / gateway / core
src/<pkg>/
  config.py                # 环境变量集中处，代码里不出现密钥
  doctor.py                # 环境自检：版本配对、端口、Key、连通性
  store.py                 # SQLite：消息 / 摘要 / 去重
  memory.py                # 滑动窗口 + 滚动摘要
  prompt.py                # 群聊人格与硬规则
  llm.py                   # OpenAI 兼容客户端，自带重试
  pipeline.py              # 触发、清洗、分条、限流（纯函数）
  agent.py                 # 编排，平台无关
  core_api.py              # FastAPI 暴露核心
  gateway/
    base.py                # 抽象 + dispatch/deliver
    wcferry_gw.py          # 微信个人号实现
```

## 十、坑清单

- **版本静默失效**：程序在跑、消息收不到，九成是微信和 DLL 没配对。做个 `doctor` 命令自动比对。
- **注册表残留陷阱**：`DisplayVersion` 说有 3.9，实际目录里只有升级残留、没有 exe。必须以磁盘上的 exe 为准。
- **微信 3.9 安装器无视 `/D=`**：它硬装到 `C:\Program Files\Tencent\WeChat`，连注册表 `InstallPath` 都会被覆盖。要装别的盘只能装完用管理员搬，通常不值得。
- **企业微信误判**：以为官方机器人能进微信群，方案做完才发现只能内部群。
- **@ 识别**：只靠昵称匹配会被改名、表情符号搞挂；用 xml 的 `atuserlist`。
- **重复消息**：网关重连会重推，必须按 `msg_id` 去重。
- **SQLite 权限**：容器里用非 root 用户时，绑定挂载会继承宿主机权限导致写不进去，改用命名卷。
- **「一直开着」不可回避**：告诉用户这是硬成本，别承诺「关机也能用」。
